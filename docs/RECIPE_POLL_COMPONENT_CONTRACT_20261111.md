# Spoonie 레시피 투표 컴포넌트 운영 규약 (2026-11-11)

## 기능 범위
- `RecipePoll`: 실제 공개된 Spoonie **공식 큐레이터 레시피**에 한해 표시하는 선택형 참여 컴포넌트.
- 질문은 레시피당 1개, 선택지는 2~4개, 단일 선택. 실제 회원 한 명당 한 표. 이미 투표한 회원은 변경 가능.
- **투표 후** 실제 선택 비율·총 참여 수를 표시하며, 투표 전에는 결과를 숨긴다.
- 투표자가 없는 상태는 0명이며 가짜 참여 수/댓글/인기도/사회적 증거를 넣지 않는다.
- 비회원은 투표 UI를 볼 수 있지만 저장 시 기존 로그인 안내를 띄운다. 투표를 강제로 재개하지 않는다.
- 공식 편집 계정의 자가 투표는 서버에서 거부한다.
- 큐레이터가 아닌 일반 사용자의 레시피에는 아직 투표를 의무화하거나 임의 생성하지 않는다.

## 저장 구조
- `public.recipe_polls`: 공개 레시피 ID로 고정된 질문과 선택지. 본문 `description` 과 **분리**.
- `public.recipe_poll_votes`: `(recipe_id,user_id)` 기본 키로 중복 방지. `option_index`와 수정시각만 저장.
- RPC `get_recipe_poll`: 공개 레시피+공식 편집 계정 작성자만 공개, 집계 수치만 반환. 투표자 목록은 반환하지 않음.
- RPC `cast_recipe_poll_vote`: 로그인 정보, 계정 성격, 공개 상태, 허용된 선택지 검사 후 upsert.
- 두 테이블 모두 RLS 활성화, 일반 클라이언트 직접 테이블 권한 없음. 관리자 권한은 안전한 운영 환경에만.

## 소이 편집 계약
새 레시피 소개글을 쓰기 전 캐릭터를 정한 다음, 그 캐릭터의 관점에서 **취향에 정답이 없는 질문**을 작성한다. 최소 2개, 최대 4개의 짧고 명료한 선택지를 함께 만든다. 예를 들어:

```json
{
  "recipeId": "실제 공개 후 확정된 Recipe UUID",
  "question": "당고는 어떤 식감이 더 좋으세요?",
  "options": ["살짝 구워 고소한 향을 더한 당고", "굽지 않고 말랑하게 즐기는 당고"]
}
```

위 예시의 ID 문구는 자리 표시자이므로 **실제 운영에 쓰면 안 된다**. 레시피 제목/음식명/선택지 오류는 사람이 확인해야 한다. 사용자 참여를 강요하는 질문은 생략 가능하다. 기존 SNS용 질문이나 단순 댓글 문구와 혼동하지 않는다.

작성된 레시피가 실제 제공자에 공개됐다는 native receipt를 확인한 후, 기존 승인된 서버 관리자 환경에서 다음만 실행한다.

```sh
node scripts/operations/seed-recipe-poll.mjs /absolute/path/to/poll-spec.json
node scripts/operations/seed-recipe-poll.mjs /absolute/path/to/poll-spec.json --apply
```

첫 번째는 읽기 전용 사전 검증, 두 번째는 실제 최초 등록이며 충돌·중복·다른 저자 ID에 대한 덮어쓰기가 금지된다. **단일 게시자/기존 Netlify 공개 대기열, Windows Session Supervisor의 소이 관리 소유권은 그대로 유지**한다.

## 기존 레시피 본문
본문에 `함께 나눠요 | ...` 형태의 문구가 있어도 별도 투표가 등록되지 않았다면 그대로 보인다. 실제 투표 레코드가 있는 경우에만 이전 한 줄 질문을 소개글에서 가리고, 동일한 레시피의 투표 컴포넌트를 표시한다. 나머지 조리 사실과 사진·원작 출처는 변경되지 않는다.
